About this document
Cynovela is a completely unofficial learning tool built so that an individual can understand the concepts of an AI platform tool by working through them hands-on. It is not a commercial product or an official implementation. The implementation is entirely original and is built on an OSS stack of FastAPI / SQLite / ChromaDB / BGE-M3 / a local LLM. It does not represent the official position of any company or product in any way.

Cynovela is built with FastAPI, and its endpoints are spread across 36 files under routers/. This document is not a per-endpoint specification; it is put together so that you can see the main categories at a glance as an overall map.

API Reference 1. Authentication

1.1 Authentication header

As a rule, API requests pass the credentials in the Authorization header.

  • In normal mode you log in with a username and password, and then use the token issued by the server.
  • The only authentication is the JWT issued by POST /api/auth/login. The simple token of the form Bearer demo-token-{user_id} that used to exist was removed on 2026-07-29 and is not accepted even when started with --demo.

1.2 Authorization (permission check)

At the beginning of each endpoint, a role check helper from core/auth.py is called.

HelperWhat it checks
_require_admin()role == admin
_require_authenticated()Authenticated (any role)
_require_role(roles)Matches one of the specified roles
_require_admin_or_self()admin or the user themselves

The role check calls are spread over about 242 places.

API Reference 3. Basic request / response format

3.1 Common headers

  • Content-Type: application/json
  • Authorization: Bearer <token>
  • X-Request-ID: <uuid> … added by the server to every request (default of logging.request_id = true)

3.2 Response

JSON is the basic format. On error, the following format is returned.

{
  "error": {
    "code": "BAD_REQUEST",
    "message": "action must be 'block' or 'warn'"
  }
}

3.3 SSE (Server-Sent Events)

Streaming chat responses are returned in the SSE format.

  • For each event, event: and data: are emitted separated by newlines
  • The design also handles the case where the connection reads the DB from an SSE thread safely, via db.get_db(check_same_thread=False)

API Reference 4-6. Limits, maximums, and pagination

4. Rate limiting

  • Rate limiting using SlowAPI is enabled by default.
  • It can be disabled by setting the environment variable CYNOVELA_DISABLE_RATE_LIMIT to one of 1 / true / yes (intended for use during testing).

5. Upload limit

  • The default limit for file upload is 100 MB.
  • It can be changed with the environment variable CYNOVELA_MAX_UPLOAD_BYTES.

6. Pagination

ParameterPurpose
limitNumber of items per page (the default depends on the endpoint)
offsetStart position of the retrieval

For audit log retrieval (the MCP get_audit_logs), limit defaults to 10 with a maximum of 50.

API Reference 7. Known limitations
  • Deleting or tampering with the audit log via the API is prohibited (append only).
  • Enforced authentication works regardless of the startup form. The authentication check is not skipped even when started with --demo (the fixed token of the form Bearer demo-token-<user_id> was removed on 2026-07-29 and is uniformly rejected with 401).
  • The path parameter of /api/sources requires validation to prevent access to system paths.
  • llm_endpoint is validated so that it cannot be changed to a value pointing at the internal network.
  • When composing the LLM prompt, the design places the system prompt after retrieved_content (because placing it before would let the documents override it).
  • Some endpoints depend on features planned for the future (Qdrant, MLX, GraphRAG, and so on) and are currently only skeletons.

API リファレンス 1. 認証方式

1.1 認証ヘッダー

API リクエストは原則として Authorization ヘッダーで認証情報を渡します。

  • 通常モードでは username と password によるログインを経て、サーバー側で発行されたトークンを利用します。
  • 認証は POST /api/auth/login が発行する JWT のみです。かつて存在した Bearer demo-token-{user_id} 形式の簡易トークンは 2026-07-29 に廃止され、--demo 起動でも受理しません。

1.2 認可（権限チェック）

各エンドポイントの先頭で、core/auth.py のロール検査ヘルパーを呼び出します。

ヘルパー検査内容
_require_admin()role == admin
_require_authenticated()認証済み（ロール不問）
_require_role(roles)指定ロールのいずれかに合致
_require_admin_or_self()admin または本人

ロール検査の呼び出しは 約 242 箇所 に分散しています。

API リファレンス 3. リクエスト / レスポンスの基本形式

3.1 共通ヘッダー

  • Content-Type: application/json
  • Authorization: Bearer <token>
  • X-Request-ID: <uuid> … サーバー側で全リクエストに付与（logging.request_id = true の既定）

3.2 レスポンス

JSON 形式が基本です。エラー時は次の形式で返します。

{
  "error": {
    "code": "BAD_REQUEST",
    "message": "action must be 'block' or 'warn'"
  }
}

3.3 SSE（Server-Sent Events）

  • 接続が SSE スレッドから DB を参照する場合も db.get_db(check_same_thread=False) で安全に扱える設計

API リファレンス 4〜6. 制限・上限・ページネーション

4. レート制限

  • 既定で SlowAPI を用いたレートリミットが有効です。
  • 環境変数 CYNOVELA_DISABLE_RATE_LIMIT を 1 / true / yes のいずれかに設定すると無効化できます（テスト時の利用を想定）。

5. アップロード上限

  • ファイルアップロードの既定上限は 100 MB です。
  • 環境変数 CYNOVELA_MAX_UPLOAD_BYTES で変更できます。

6. ページネーション

パラメータ用途
limit1 ページの件数（既定はエンドポイントごと）
offset取得開始位置

監査ログ取得（MCP の get_audit_logs）の limit は既定 10 / 最大 50 です。

API リファレンス 7. 既知制限
  • API 経由での 監査ログの削除・改ざんは禁止 されています（追加のみ）。
  • 認証強制は起動形態によらず動作します。--demo 起動でも認証チェックは省かれません（Bearer demo-token-<user_id> 形式の固定トークンは 2026-07-29 に廃止し、一律 401 で拒否します）。
  • /api/sources の path パラメータは、システムパスへのアクセスを防ぐためのバリデーションが必要です。
  • llm_endpoint は内部ネットワークを指す値に変更できないようにバリデーションされます。
  • LLM プロンプトを構成する際、システムプロンプトは retrieved_content の 後 に配置する設計です（前置きするとドキュメントで上書き可能になるため）。
  • 一部のエンドポイントは将来実装予定の機能（Qdrant、MLX、GraphRAG など）に依存しており、現状は骨格のみです。

Security Policy About This Document
About This Document
Cynovela is a completely unofficial learning tool, built so that one individual can understand the concepts of an AI platform tool by working on them hands-on. It is not a commercial product or an official implementation. Everything is implemented originally, on an OSS stack of FastAPI / SQLite / ChromaDB / BGE-M3 / a local LLM. It does not represent the official view of any company or product in any way.

Cynovela is a learning tool and does not meet the security requirements of production operation. This document organizes the explicit disclaimers, the known limitations as of Alpha GA, and the usage that is not recommended.

Security Policy 2-1. Known Limitations — Authentication and Authorization
  • Authentication is JWT: issued by POST /api/auth/login, and required even in a --demo start. The old Bearer demo-token-<user_id> form was abolished on 2026-07-29.
  • No API key management feature: issuing and revoking per-user API keys is not implemented.

2-2. Communication encryption

  • HTTPS not supported: the application itself listens over HTTP only. TLS termination must be delegated to a reverse proxy (nginx, etc.).
  • LLM communication is also plaintext: connections to LM Studio / Ollama are plaintext HTTP as well. Publishing outside the LAN is not recommended.
  • The old transcribe audio path has been removed: the router was disabled to close the egress hole for raw PII, and voice.py takes its place.

2-3. Settings that are not persisted

  • Embedding / Reranker settings: changes made at run time (through the UI) are not persisted to the YAML and revert to the defaults on restart.
Cynovela Unofficial / personal learning / Alpha GA
Security Policy 2-4. Known Limitations — Skeleton-only Features
  • Qdrant VectorStore: only the abstraction layer and a connection stub. add / search / delete_collection / export / import_data are not implemented.
  • MLX Embedding: NotImplementedError. The Apple Silicon optimized version is future work.
  • MLX Reranker: NotImplementedError. Future work.
  • LanceDB backend: initialization only; the substance is not implemented.
  • GraphRAG strategy: only the abstract class; retrieve / build_graph / traverse_with_acl are not implemented.

Security Policy 2-5 to 2-7. Known Limitations — Others

2-5. DataSyncService

  • publish integration not merged: the hash-difference synchronization only writes logs, and the actual connection to rag.publish is a noop.
  • No content_hash comparison: difference detection is currently per path only (addition / deletion). Detecting content changes is not supported.

2-6. RAG pipeline

  • Structured answer template not implemented: free-form answers are the standard. Forcing an answer in JSON form or XML tag form is not supported.
  • Low-confidence fallback partially implemented: confidence_threshold (0.50) is defined, but the processing that automatically switches to GENERAL_KNOWLEDGE_SYSTEM_PROMPT when there are 0 search results is not integrated.

2-7. UI

  • Some elements of the i18n switch: some of the elements whose display is controlled by the language switch (Japanese / English) are fixed.
  • Hiding before tab initialization: some UI elements are display:none until the JavaScript initialization.

Security Policy 2-8. Areas Skipped in the Tests

  • Sources API: because of the path registration form, 2 tests are skipped.
  • Publish Semaphore: 1 xfail because injecting a mock at module scope is difficult. A lazy accessor is planned in Stage-3.

Security Policy 3. Usage That Is Not Recommended

The following ways of use are either not blocked by design or are blocked incompletely, so please do not do them.

3-1. Publishing directly to the Internet

Opening a port directly to the Internet while bound to 0.0.0.0 with --lan is strictly prohibited. The reasons are as follows.

  • HTTPS is not in place (plaintext communication)
  • JWT authentication is not implemented
  • RBAC enforcement is limited
  • The file upload restrictions are loose

3-2. Production operation with confidential documents

  • Fernet encryption of the raw text is in operation, but key management (CYNOVELA_SECRET_KEY) assumes personal operation
  • Tamper protection of audit_logs applies only through the API; direct DB access is out of scope of the protection
  • Mechanisms for backup and disaster recovery are not implemented

Security Policy 3. Usage That Is Not Recommended (Continued) (2/2)

3-3. LAN sharing with untrusted users

When sharing over the LAN, the premise is that every user on the network is trusted. It is recommended to narrow the connection sources strictly with --allow-subnet and then use it only among trusted members.

3-4. Editing the audit log directly in the DB

Modifying or deleting the audit_logs table through the API is prohibited. Editing the DB directly (with the sqlite3 command and so on) also leads to breaking consistency, so please avoid it.

3-5. Forcing multiple simultaneous Publish runs

Running multiple Publish operations on the same Collection at the same time is prevented with collection_locks, but forcibly releasing the DB lock and running them in parallel leads to breaking data consistency.

3-6. Checking quality in mock mode

Always run the RAG quality verification tests in an environment where a real LLM (LM Studio, etc.) is running. The --mock option that used to exist (which ran without calling an LLM) has been removed.

3-7. Adding new INSERT OR REPLACE statements

INSERT OR REPLACE fires the SQLite FK CASCADE unintentionally, so it is prohibited in the codebase. To update an existing row, use INSERT ... ON CONFLICT(id) DO UPDATE SET ....

Security Policy 4. Recommended Operating Configurations

One of the following configurations is recommended.

4-1. Fully local operation (the safest)

python server.py --demo
  • Binds to 127.0.0.1 only
  • The LLM is a mock as well
  • For verification, demonstrations, and tutorials

4-2. Local LLM operation

python server.py --demo --lmstudio-url http://localhost:1234
  • Start LM Studio or Ollama on the same machine
  • No network exposure
  • For personal learning and experimentation

セキュリティ ポリシー 3. 推奨しない使用方法

以下の使い方は仕様上ブロックされていないか、ブロックが不完全なため、行わないでください。

3-1. インターネットへの直接公開

--lan で 0.0.0.0 バインドした状態でインターネット側に直接ポート開放することは厳禁です。理由は次のとおりです。

  • HTTPS 化されていない（平文通信）
  • JWT 認証が未実装
  • RBAC 強制が限定的
  • ファイルアップロード制限が緩い

3-2. 機密文書での本番運用

  • raw 本文の Fernet 暗号化は稼働中だが、鍵管理（CYNOVELA_SECRET_KEY）は個人運用前提
  • audit_logs の改ざん防止は API 経由のみで、DB 直接アクセスは保護対象外
  • バックアップ・ディザスタリカバリの仕組みは未実装

セキュリティ ポリシー 3. 推奨しない使用方法（続き） (2/2)

3-3. 信頼できないユーザーへの LAN 共有

LAN 共有時は、ネットワーク上の全ユーザーが信頼できる前提です。--allow-subnet で接続元を厳密に絞ったうえで、信頼できるメンバーのみでの利用を推奨します。

3-4. 監査ログの DB 直接編集

audit_logs テーブルへの API 経由の変更・削除は禁止しています。DB 直接編集（sqlite3 コマンド等）も整合性破壊につながるため避けてください。

3-5. 同時複数 Publish の強制実行

同一 Collection への複数 Publish 同時実行は collection_locks で防いでいますが、強制的に DB ロックを解除して並列実行することはデータ整合性破壊につながります。

3-6. モックモードでの品質確認

RAG 品質確認テストは必ず実 LLM（LM Studio など）起動環境で行ってください。以前あった --mock（LLM を呼ばずに動かす指定）は撤去済みです。

3-7. INSERT OR REPLACE 文の新規追加

INSERT OR REPLACE は SQLite の FK CASCADE を不本意に発火させるため、コードベースで使用禁止です。既存行更新は INSERT ... ON CONFLICT(id) DO UPDATE SET ... を使用してください。

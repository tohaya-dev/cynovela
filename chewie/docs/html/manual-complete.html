Chapter 1 — Overview
Complete Manual 1-1. What Is Cynovela

Cynovela is a completely unofficial learning tool built by an individual to understand the concepts behind AI platform tools by hands-on work.

It is designed so you can experience "what it looks like when you actually build it" for features such as the following, which the referenced AI platform tools provide.

  • Data governance (guardrails, PII detection, audit logs)
  • Data ingest (automatic classification, metadata extraction, incremental sync)
  • RAG (retrieval-augmented generation) pipeline
  • Role-based access control (RBAC)
  • MCP (Model Context Protocol) integration

Complete Manual 1-2. Design Concepts

Cynovela is designed with the top priority of "not stopping at reading, but learning by running it yourself".

  • No missing core features: essential features such as guardrails / PII / RAG / RBAC / audit logs are not omitted; they are implemented in a simplified form.
  • Built from OSS only: it uses only easily obtainable OSS, such as FastAPI, SQLite, ChromaDB, BAAI/bge-m3, and cryptography (Fernet).
  • Fully local: by default it assumes a connection to a local LLM runner such as LM Studio or Ollama. No cloud dependency.
  • Idempotent and non-destructive: schema changes consistently useCREATE TABLE IF NOT EXISTS andALTER TABLE wrapped intry/except, and data updates useINSERT ... ON CONFLICT DO UPDATE.

Chapter 2 — Concepts of AI Governance
Complete Manual 2-1. Data Classification and Labeling

This chapter organizes, from eight points of view, how Cynovela reproduces the governance features that AI platform tools have in common. This is the mechanism that mechanically decides "what kind of thing" each document is and attaches a label to it. Cynovela defines 14 categories.

  • Governance and policy documents / incident reports / technical guides and manuals
  • Case studies / meeting minutes / audit and assessment reports / POC evaluation reports
  • FAQs / white papers / checklists
  • Proposals and RFPs / newsletters and technical information / references and glossaries / other

In addition, it performs a supplementary classification into 5 document formats (contract, technical specification, email, report, manual).

Complete Manual 2-3. Access Control (RBAC)

This is the mechanism that restricts the information a user can see and the operations a user can perform according to the user's role.

RoleDescription
adminFull administrative rights
viewerView only
Names such ascurator /data-scientist are accepted as backward-compatible values, but in the current implementation they are normalized toviewer and carry no specific rights (the effective roles are the two valuesadmin /viewer).

RBAC is checked in 33 routers (242 places) and is consolidated into 4 helper functions (_require_admin,_require_authenticated,_require_role,_require_admin_or_self).

Complete Manual 2-4. Audit Logs / 2-5. Guardrails

2-4. Audit logs

Important operations (creating and deleting a Source or Workspace, Publish, Chat, PII detection, authentication failure, and so on) are recorded in a form that cannot be tampered with. Cynovela forbids changing or deleting rows of theaudit_logs table through the API.

2-5. Guardrails

This is the mechanism that defines how to deal with detected information and with input queries. Cynovela has 4 kinds of actions.

ActionBehavior
maskReplace the matched part with a mask token ([MASKED:EMAIL] and so on)
exclude_from_ragExclude it from RAG search
log_onlyOnly record the detection, take no action
allowAllow (explicitly allowlisted)

A policy is combined with several classification classes (PII, Financial, HR) and bound to a Workspace. The seed data provides 3 of them:pol-pii,pol-strict, andpol-log.

Complete Manual 2-6. Encryption

Highly confidential raw text (the data before masking) is stored encrypted with Fernet (symmetric-key encryption).

  • Key management: theCYNOVELA_SECRET_KEY environment variable (generated automatically when not specified; specifying it explicitly is recommended in production)
  • Targets: thechunks /parent_chunks tables in SQLite and the*__raw collections in ChromaDB
  • Format: theenc: prefix plus a base64 string (idempotent, no double encryption)

Complete Manual 2-7. Countermeasures Against Prompt Injection

To prevent malicious instruction injection into the LLM, a 3-layer defense is implemented.

  1. Input inspection: if the query contains any of 14 English and Japanese injection patterns (ignore previous instructions,これまでの指示を無視, and so on), it is blocked immediately with HTTP 400.
  2. Post-retrieval inspection: chunks in the search results that contain injection wording are excluded.
  3. Output inspection: the LLM response is checked forHACKED /PWNED /SECRET-ALPHA-TOKEN /[SYSTEM OVERRIDE].

On detection,PROMPT_INJECTION_BLOCKED is recorded inaudit_logs.

Cynovela Unofficial, for personal learning
Complete Manual 2-8. Data Minimization (Dual-Tier Storage)

For the same document, raw (the original text) and masked (the masked text) are stored in separate records and separate vector collections, so that the source referred to is switched according to the role.

  • admin role: refers to the raw collection ({cid}__raw, Fernet encrypted)
  • Other roles: refer to the masked collection ({cid}__masked)

In addition,_mask_for_viewer is also applied to the LLM output, which gives a second layer of defense.

Chapter 4 — Basic Operations
Complete Manual 4-1. Core Flow (Steps 1–3)

The main operations of Cynovela follow the flow below.

Source 登録 → Scan → Workspace 作成 → Collection 作成 → Publish → RAG Chat

Step 1: Register a Source

Register the origin of the data (a local folder). POST a path to/api/sources, or register it from the UI with the "Add Source" button.

Step 2: Scan

The files under the registered Source are scanned and records are created in thefiles table. Each file is given a deterministic ID derived from its path (_stable_fid(path)).

Step 3: Create a Workspace

A Workspace is "the unit that groups several Collections" and also "the unit that binds a guardrail policy and users together".

Cynovela Unofficial, for personal learning
Complete Manual 4-1. Core Flow (Steps 4–6) (2/2)

Step 4: Create a Collection

A Collection is the unit of "a set of files plus a classification and chunking strategy". Its state moves throughdraft → ingested → publishing → ready.

  • rag_strategy:simple /hybrid_bm25 (default) /contextual
  • chunk_size,chunk_overlap
  • access_level:public /internal /confidential
  • allowed_roles_json: the ACL (access control list)

Step 5: Publish

The files in the Collection are split into chunks, turned into vectors, and put into ChromaDB. At Publish time the following happen at the same time.

  • Generation of chunks for both the raw and the masked tier
  • PII detection and Fernet encryption (raw side only)
  • Building the BM25 index
  • Recording intopublish_history (doc_count, chunk_count, pii_count, excluded_count, elapsed_seconds, and so on)

Step 6: RAG Chat

When the user enters a question, the pipeline of search → reranker → LLM generation → guardrail application → returning the answer is executed.

Chapter 5 — Design Details
Complete Manual 5-1. RAG Pipeline — Main Flow

The main functionrag_retrieve() executes the following flow.

1. Vector Search (ChromaDB)
   ├ MMR（多様性確保）
   └ ACL フィルタリング
2. BM25 Search（メモリ内インデックス）
   ├ トークン化（日本語: fugashi、英語: 空白区切り）
   └ ACL フィルタリング
3. Hybrid Integration
   └ RRF（k=60、既定）または重み付け（vector 0.7 + bm25 0.3）
4. Parent-Child 解決
   └ child hit を parent テキストに置換
5. Reranker 適用
   └ CrossEncoder / BGE-Reranker など
6. Final Ranking
   └ Top n_results 件を返却

Complete Manual 5-3. Smart Ingestion — Incremental Sync and Chunking (2/2)

Hash-based incremental sync

DataSyncService scans thesources table periodically.

  • Default interval: 60 seconds (minimum 10 seconds)
  • Compared against: the (source_id, path) records of thefiles table
  • Difference detection: additions and removals in the set of paths

Integration with publish is not wired up; at present it only writes to the log.

Chunk splitting

  • Default: a sliding window of 500 characters with 50 characters of overlap
  • When Contextual Chunking is enabled: metadata (file name, kind, sensitivity, department, position, tags) is prepended to the chunk

Complete Manual 5-4. Guardrails and PII (recap)

Tier1 (masking at ingest time)

At Publish time a dual row of raw / masked is generated from each chunk. Two collections,{cid}__raw and{cid}__masked, are created in ChromaDB. Two rows,tier='raw' andtier='masked', are also stored in the SQLitechunks table.

Tier2 (masking at answer time)

_mask_for_viewer is applied to the LLM output in 4 places on the chat path (normal / compare A / compare B / SSE). Masking is forced for everyone except admin.

Fernet encryption

Theenc_raw /dec_raw interface ofvault_enc.py (theenc: prefix, idempotent). Only the raw tier is encrypted; the masked tier passes through as is.

Chapter 7 — Known Limitations
Complete Manual 7-1 to 7-3. Known Limitations

7-1. Authentication and authorization

  • Authentication uses JWT (issued byPOST /api/auth/login, required even with--demo). The oldBearer demo-token-<user_id> form has been removed
  • There is no per-user API key issuing feature

7-2. Transport encryption

  • HTTPS is not supported (you need to terminate TLS at a reverse proxy)
  • Traffic to the LLM is also plaintext HTTP

7-3. Settings that are not persisted

  • Run-time changes to the embedding and reranker settings are not persisted to the YAML (they return to the defaults on restart)
Cynovela Unofficial, for personal learning
Complete Manual 7-4 to 7-7. Known Limitations

7-4. Features that are only a skeleton

  • The Qdrant VectorStore (add /search and so on raiseNotImplementedError)
  • MLX embedding / reranker (NotImplementedError)
  • The LanceDB backend
  • The GraphRAG strategy

7-5. DataSyncService

  • Integration with publish is not wired up (it only writes to the log)
  • No content_hash comparison (differences are detected per path only)

7-6. RAG pipeline

  • Structured answer templates are not implemented (free-form answers are the standard)
  • The low-confidence fallback is only partly implemented

7-7. UI

  • Some UI elements aredisplay:none until JavaScript initializes
  • When switching the language (Japanese / English), some elements stay fixed

Chapter 8 — FAQ
Complete Manual Q1. How are ChromaDB and SQLite used differently?
  • SQLite: metadata (structured information such as Workspace, Collection, Source, File, User, AuditLog, and PublishHistory)
  • ChromaDB: vector embeddings and the chunk text (for search)

The two are deleted in sync by the_purge_chunks_for_*() helpers.

Complete Manual Q2. What happens if I lose the Fernet key?

The raw text (the part that is Fernet encrypted) can no longer be decrypted. The masked text passes through as is, so it can still be read, but even the admin role can no longer see the raw text. KeepCYNOVELA_SECRET_KEY in a safe place.

AI 基盤ツールに共通するガバナンス機能を、Cynovela がどのように再現しているかを 8 つの観点で整理します。文書ごとに「何の種類か」を機械的に判断し、ラベルを付与する仕組みです。Cynovela は 14 種類のカテゴリを定義しています。

完全マニュアル 2-3. アクセス制御（RBAC）

ユーザーのロールに応じて、見られる情報と実行できる操作を制限する仕組みです。

ロール説明
adminフル管理権限
viewer閲覧のみ
curator /data-scientist 等の名称は後方互換の値として受理されますが、現行実装ではviewer に正規化され、固有権限はありません（実効ロールはadmin /viewer の 2 値）。

完全マニュアル 2-4. 監査ログ・2-5. ガードレール

2-4. 監査ログ

重要操作（Source / Workspace 作成・削除、Publish、Chat、PII 検出、認証失敗 など）を改ざんできない形で記録します。Cynovela はaudit_logs テーブルへの API 経由の変更・削除を禁止しています。

2-5. ガードレール

検出した情報や入力クエリに対して、どう対処するかを定義する仕組みです。Cynovela のアクションは 4 種類です。

アクション動作
mask該当箇所をマスクトークン（[MASKED:EMAIL] 等）に置換
exclude_from_ragRAG 検索対象から除外
log_only検出のみ記録、アクションは取らない
allow許可（明示的にホワイトリスト化）

ポリシーは複数の分類クラス（PII、Financial、HR）と組み合わせて Workspace に紐付きます。シードデータではpol-pii、pol-strict、pol-log の 3 種が用意されています。

完全マニュアル 2-6. 暗号化

機密度の高い raw 本文（マスク前データ）は Fernet（対称鍵暗号）で暗号化されて保存されます。

  • 鍵管理:CYNOVELA_SECRET_KEY 環境変数（無指定時は自動生成、本番運用では明示推奨）
  • 対象: SQLite のchunks /parent_chunks テーブルおよび ChromaDB の*__raw コレクション
  • 形式:enc: プレフィックス + base64 文字列（冪等、二重暗号化なし）
Cynovela 非公式・個人学習目的
完全マニュアル 2-7. プロンプトインジェクション対策

LLM への悪意ある指示注入を防ぐため、3 層防御を実装しています。

  1. 入力検査: クエリに 14 種の英日インジェクションパターン（ignore previous instructions、これまでの指示を無視 等）が含まれていれば HTTP 400 で即遮断。
  2. Retrieval 後検査: 検索結果のチャンクからインジェクション文言を含むものを除外。
  3. 出力検査: LLM 応答にHACKED /PWNED /SECRET-ALPHA-TOKEN /[SYSTEM OVERRIDE] が含まれていないか確認。

検出時はaudit_logs にPROMPT_INJECTION_BLOCKED を記録します。

Cynovela 非公式・個人学習目的
完全マニュアル 2-8. データ最小化（Dual-Tier 保管）

同じ文書について、raw（生本文）と masked（マスク済み本文）を別々のレコード・別々のベクターコレクションに保存することで、ロールに応じて参照先を切り替えます。

  • admin ロール: raw コレクション（{cid}__raw、Fernet 暗号化）を参照
  • その他のロール: masked コレクション（{cid}__masked）を参照

加えて、LLM 出力にも_mask_for_viewer を適用して二重防御を実現しています。

第 4 章　基本操作
完全マニュアル 4-1. コアフロー（Step 1〜3）

Cynovela の主要操作は以下のフローに沿って進みます。

Source 登録 → Scan → Workspace 作成 → Collection 作成 → Publish → RAG Chat

Step 1: Source 登録

データの取得元（ローカルフォルダ）を登録します。/api/sources にパスを POST するか、UI から「Source 追加」ボタンで登録します。

Step 2: Scan

登録した Source 配下のファイルを走査し、files テーブルにレコードを作成します。各ファイルにはパス由来の決定論的 ID（_stable_fid(path)）が振られます。

Step 3: Workspace 作成

Workspace は「複数の Collection をまとめる単位」かつ「ガードレールポリシーとユーザーを紐付ける単位」です。

Cynovela 非公式・個人学習目的
完全マニュアル 4-1. コアフロー（Step 4〜6） (2/2)

Step 4: Collection 作成

Collection は「ファイル群 + 分類・チャンク戦略」の単位です。状態はdraft → ingested → publishing → ready と遷移します。

  • rag_strategy:simple /hybrid_bm25（既定）/contextual
  • chunk_size、chunk_overlap
  • access_level:public /internal /confidential
  • allowed_roles_json: ACL（アクセス制御リスト）

Step 5: Publish

Collection 内のファイルをチャンク化・ベクター化して ChromaDB に投入します。Publish 時には次が同時に行われます。

  • raw / masked 両 tier のチャンク生成
  • PII 検出と Fernet 暗号化（raw 側のみ）
  • BM25 インデックス構築
  • publish_history への記録（doc_count、chunk_count、pii_count、excluded_count、elapsed_seconds など）

Step 6: RAG Chat

ユーザーが質問を入力すると、検索 → Reranker → LLM 生成 → ガードレール適用 → 回答返却、というパイプラインが実行されます。

PII 検出モードを確認してください。lite は正規表現のみのため、住所などの自然言語 PII は検出されません。standard またはquality に変更すると GiNZA NER による住所・人名・組織名の検出が有効になります。

完全マニュアル Q6. MCP クライアントから接続できません

以下を確認してください。

  • Cynovela 本体（server.py）がhttp://127.0.0.1:8765 で起動済みか
  • CYNOVELA_TOKEN 環境変数の値、トークンの有効性
  • CYNOVELA_MCP_PYTHON で conda 環境の Python パスを指定済みか
  • 対象 Collection がready ステータスに到達済みか

完全マニュアル Q7. インターネットに公開しても良いですか？

絶対に推奨しません。HTTPS 化されておらず、JWT 認証も未実装、ファイルアップロード制限も緩いため、インターネット直接公開は重大なリスクがあります。

完全マニュアル Q8. データを完全に削除するには？

UI から Source / Workspace / Collection を削除すれば、SQLite と ChromaDB の両方が_purge_chunks_for_*() 系ヘルパー経由でクリーンアップされます。完全初期化したい場合は~/.cynovela ディレクトリ全体を削除してください（バックアップは事前に取得してください）。

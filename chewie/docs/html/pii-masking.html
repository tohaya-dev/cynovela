pii-masking 1. Design principle: only masked text goes into ChromaDB

The basic policy against PII (Personally Identifiable Information: personal data and confidential internal information) is this: the vector DB (ChromaDB), which is broadly exposed as a search target, holds only masked text as a rule. The raw text is stored encrypted in a separate lane, and can only be retrieved by the administrator role.

With this design, the leak paths are narrowed even in the following situations.

  • The path where a search hit is mixed into the LLM prompt → only masked text is passed
  • The path where the ChromaDB data is dumped or copied as is → masked only
  • The path where the DB file is physically carried away → the raw side is already encrypted with Fernet

To achieve this, Cynovela uses a double defense of masking at ingest time (Tier1) and masking at answer time (Tier2).

Removed (2026-07-24): the former exception "ingest without masking" (collections.raw_only) has been removed. Ingest always goes through masking, and there is only one set of vectors, the masked one. The columns for past data remain for preservation (see metadata-engine §6 for details).

pii-masking 2. Tier1: masking at ingest time

2.1 Role

In the middle of Publish (the processing that pushes a collection into ChromaDB), a dual-row of "raw text" and "masked text" is generated for each chunk. Both are stored in the SQLite chunks table and in both ChromaDB collections.

2.4 Behavior on failure

Even if the masking raises an exception, Publish is not stopped: it is logged with _log.warning, and then the raw text is stored on the masked side as well. This design avoids the risk that "if ingest stops, the business stops".

pii-masking 3. Tier2: masking at answer time

3.1 Role

An additional exit mask is applied to the answer text generated by the LLM, according to the role of the user. This makes sure that even if raw text somehow gets mixed into the context, it never reaches a user other than admin.

3.2 Implementation (routers/chat.py:128-162)

def _mask_for_viewer(text: str, user: dict | None) -> str:
    """M1: 利用者の保管庫 tier (raw/masked) に応じて
    LLM 生成出力に出口マスクを適用する。"""
    if not text or not user:
        return text
    try:
        from rag import tier_for_role
        if tier_for_role(user.get("role") or "") == "raw":
            return text
    except Exception:
        pass
    try:
        from guardrail import mask_text_with_spans
        masked, _spans = mask_text_with_spans(text)
        return masked
    except Exception:
        return text

_mask_for_viewer is called at 4 places on the chat path (normal response / Compare A / Compare B / SSE path).

def tier_for_role(role: str) -> str:

tier_for_role decides both which ChromaDB store is queried ({cid}__raw or {cid}__masked) and whether the exit mask is applied or bypassed, so it works as a double defense.

pii-masking 4. Fernet encryption

4.1 Role

Right before the raw tier text is stored into SQLite and ChromaDB, it is encrypted with Fernet (a symmetric-key encryption scheme: authenticated AES-128-CBC + HMAC) and stored with the prefix enc:. The implementation is idempotent (a string that already starts with enc: is not encrypted again), which avoids double encryption.

4.2 Implementation

  • Key management: Fernet(_KEY) is initialized at config.py:62. The key is passed through the CYNOVELA_SECRET_KEY environment variable. For production operation, setting this environment variable explicitly is recommended.
  • Interface: enc_raw(text) / dec_raw(text) in vault_enc.py provide a thin wrapper.

pii-masking 1. 設計思想：マスク済みのみ ChromaDB へ

PII（Personally Identifiable Information：個人情報・社外秘情報）対策の基本方針は、「検索対象として広く露出するベクター DB（ChromaDB）には、原則としてマスク済みの本文だけを入れる」というものです。生本文（raw）は別系統で暗号化保管し、管理者ロールに限って引き出せるようにします。

この設計により、次のような状況でも漏えい経路を絞れます。

  • 検索ヒットして LLM プロンプトに混入する経路 → マスク済み本文のみが渡る
  • ChromaDB のデータをそのままダンプ・コピーされる経路 → マスク済みのみ
  • DB ファイルを物理的に持ち去られる経路 → raw 側は Fernet で暗号化済み

これを実現するため、Cynovela は取込時マスキング（Tier1）と回答時マスキング（Tier2）の二重防御を採用しています。

廃止（2026-07-24）: かつての例外「マスキングなし取り込み（collections.raw_only）」は廃止されました。取り込みは常にマスキングを経由し、ベクターはマスキング済みの一組のみです。過去データの列は保全のため残っています（詳細は metadata-engine §6）。

pii-masking 4. Fernet 暗号化

4.1 役割

raw tier の本文を SQLite と ChromaDB に保存する直前に Fernet（対称鍵暗号方式の一つで、認証付きの AES-128-CBC + HMAC）で暗号化し、enc: というプレフィックス付きで保存します。冪等な実装（既に enc: で始まる文字列は再暗号化しない）になっており、二重暗号化を避けます。

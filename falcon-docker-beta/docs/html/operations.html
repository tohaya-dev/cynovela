About This Document
Cynovela is a completely unofficial learning tool built by an individual in order to understand the concepts of AI infrastructure tools hands-on. It is not a commercial product and not an official implementation. The implementation is entirely original and is built on an OSS stack of FastAPI / SQLite / ChromaDB / BGE-M3 / a local LLM. It does not represent the official view of any company or product in any way.

This document collects the procedures for starting and stopping, backup, logs, and user management needed to operate Cynovela day to day.

Operations Guide 1. Normal Startup and Shutdown

Startup

conda activate cynovela
python server.py --demo

For details of the options, see the deployment guide.

Shutdown

SendCtrl + C once in the terminal. The FastAPI / Uvicorn shutdown hook runs, and a stop request is propagated to any Publish job in progress (the SSE path).

Starting in the background

You can also keep it resident withnohup, or with a terminal multiplexer such astmux /screen.

nohup python server.py --demo > ~/cynovela.out 2>&1 &

Operations Guide 2. Backup and Restore (2/3)

Manual backup

With the server stopped, copy the directories above.

# サーバー停止後に実行
TS=$(date +%Y%m%d-%H%M%S)
mkdir -p ~/cynovela-backups/$TS
cp -R ~/.cynovela/db ~/cynovela-backups/$TS/db
cp -R ~/.cynovela/vector ~/cynovela-backups/$TS/vector

Restore

# サーバー停止後に実行
cp -R ~/cynovela-backups/20260526-093000/db ~/.cynovela/db
cp -R ~/cynovela-backups/20260526-093000/vector ~/.cynovela/vector

Operations Guide 2. Notes on Backup Operations (3/3)
  • Alwaysback up and restore SQLite and ChromaDB together. If you restore only one of them, consistency between thechunks table and the vector IDs breaks.
  • Deleting a source, workspace, or collection is implemented so that both SQLite and ChromaDB are cleaned up. Keep this "both from the same snapshot" principle in backup operations as well.
  • Starting with--demo usesdb/demo.db andvector/demo/chroma, and the demo data is reset on every start. Do not mix it with production operation.

Operations Guide 3. Log Files

Log level

Controlled bylogging.level (orserver.log_level) incynovela.yaml. The default isINFO.

logging:
  level: INFO
  request_id: true   # 全リクエストに X-Request-ID を付与

Request ID

Whenrequest_id: true is enabled, anX-Request-ID header is added to every API response. It can be used during troubleshooting to link a client-side request with the server-side log.

Preflight log

[Cynovela] PII detection mode: standard (from cynovela.yaml)

Operations Guide 4. Exporting the Audit Log

What the audit log is

Cynovela records important operations in theaudit_logs table in SQLite.

Main things that are recorded

  • Creation and deletion of workspaces, collections, and sources
  • Execution and completion of Publish
  • Chat (questions and answers)
  • PII detection (PII_DETECTED /pii_detected)
  • Prompt injection detection (PROMPT_INJECTION_BLOCKED)
  • Authentication failures
Tamper prevention:audit_logs cannot be deleted or modified through the API. Keep this principle in your operational policy as well.

Operations Guide 4. How to Read the Audit Log (2/2)

Reading it from the GUI

After logging in with theadmin role, you can browse it with filters on the "Audit log" screen.

Through the API

  • GET /api/guardrails/pii-detections — aggregates PII detections fromaudit_logs (administrator required)
  • GET /api/pii-detections — aggregates from thechunks table (administrator required)
  • GET /api/audit-logs — retrieves the audit log (administrator required)

Extracting directly from SQLite

sqlite3 ~/.cynovela/db/cynovela.db \
  "SELECT timestamp, action, target, detail FROM audit_logs ORDER BY timestamp DESC LIMIT 100;"

Operations Guide 5. Authentication / Vault / IP Access Control (2/2)

Adding and deleting users, and changing passwords

After logging in with the administrator role, you can do this from the "User management" screen. Operating through the API is also possible, but the user management endpoints are protected by_require_admin or_require_admin_or_self (only the user themselves or an administrator).

Vault access and masking by role

  • admin → searches the raw (unmasked body text) vault. No exit masking is applied to the displayed answer.
  • viewer (curator and others are normalized to viewer) → searches the masked vault. Exit masking is applied.
However, when an external (non-local) LLM is used, crag-egress-guard keeps the raw pre-read (context_preview) from being sent outside even for an administrator (CRAG is skipped). Note that it is not the case that "administrator = the raw body text is always passed to the external LLM".

Authentication

API authentication is done with the HTTPAuthorization header. The token is the JWT issued byPOST /api/auth/login. The oldBearer demo-token-{user_id} form has been removed and is not accepted.

Note: Production authentication with JWT is not implemented as of alpha GA. For details, see "Known limitations".

IP access control

By default, access is allowed only from127.0.0.1 /localhost. Access from a LAN or from Tailscale is opened up individually with startup options (--lan /--allow-tailscale /--allow-subnet).

Main health endpoints

/api/health and other monitoring endpoints for administrators are provided (protected by_require_admin).

The Publish result of each collection is recorded in thepublish_history table.

Recorded items

  • timestamp

  • chunk_count
  • pii_count

Operations Guide 6. Circuit Breaker (2/2)

When failures of LLM or external API calls exceed a certain count, the circuit breaker goes OPEN and calls are stopped temporarily. You can adjust the behavior in thecircuit_breaker section ofcynovela.yaml.

circuit_breaker:
  enabled: true
  failure_threshold: 3
  recovery_timeout_seconds: 30

Operations Guide 8. Operational Notes
  • --demo mode is for verification. The demo DB is reset on every start, so do not put production data there.
  • The--mock mode that used to exist has been removed. Specifying it now stops with an error.
  • Take backups as a snapshot of "SQLite and ChromaDB at the same time". Restoring only one of them breaks consistency.
  • audit_logs needs tamper prevention. Avoid careless writes to the SQLite file itself.

運用ガイド 2. バックアップ運用上の注意点 (3/3)
  • SQLite と ChromaDB は必ず一緒にバックアップ・復元してください。片方だけ復元するとchunks テーブルとベクター ID の整合性が崩れます。

  • --demo 起動はdb/demo.db とvector/demo/chroma を使い、起動ごとにデモデータがリセットされます。本運用と混ぜないでください。

運用ガイド 4. 監査ログのエクスポート

監査ログとは

Cynovela は重要操作を SQLite のaudit_logs テーブルに記録します。

主な記録対象

  • ワークスペース・コレクション・ソースの作成と削除
  • Publish の実行と完了
  • チャット（質問・回答）
  • PII 検出（PII_DETECTED /pii_detected）
  • プロンプトインジェクション検出（PROMPT_INJECTION_BLOCKED）
  • 認証失敗
改ざん防止:audit_logs は API 経由での削除・変更ができません。運用ポリシー上もこの原則を守ってください。

運用ガイド 5. 認証 / 保管庫 / IP アクセス制御 (2/2)

ユーザー追加・削除・パスワード変更

admin ロールでログイン後、「ユーザー管理」画面から実行できます。API での操作も可能ですが、ユーザー管理系エンドポイントは_require_admin または_require_admin_or_self（本人か admin のみ）で保護されています。

ロール別の保管庫アクセスとマスキング

  • admin → raw（生本文）保管庫を検索。回答表示では出口マスクなし。
  • viewer（curator 等は viewer に正規化）→ masked（マスク済み）保管庫を検索。出口マスクあり。
ただし外部（非ローカル）LLM を使う場合は、crag-egress-guard により admin でも raw の下読み（context_preview）が外部へ送出されません（CRAG スキップ）。「admin＝常に生本文が外部 LLM へ渡る」ではない点に注意してください。

認証

API 認証は HTTPAuthorization ヘッダーで行います。トークンはPOST /api/auth/login が発行する JWT です。旧Bearer demo-token-{user_id} 形式は廃止済みで受理しません。

注意: JWT による本番認証は alpha GA 時点で未実装です。詳しくは「既知の制限」を参照してください。

IP アクセス制御

既定では127.0.0.1 /localhost のみアクセスを許可します。LAN や Tailscale からのアクセスは起動オプション（--lan /--allow-tailscale /--allow-subnet）で個別に開放します。
